# Add a dev-only Dockerfile.dev and compose.yaml alongside the production Dockerfile

Rails generates a production-oriented `Dockerfile` (`BUNDLE_WITHOUT="development"`, `BUNDLE_DEPLOYMENT=1`, asset precompile, no test gems) that can't run the test suite or hot-reload local code. Rather than adapting it with build args/targets, we added a separate `Dockerfile.dev` (installs all gem groups, no deployment/precompile flags) plus a `compose.yaml` defining `web`, `db` (Postgres), and `test` services, with the app code volume-mounted for live reload.

The `test` service exists as its own entry (rather than expecting `RAILS_ENV=test` to be passed by hand against `web`) with `RAILS_ENV=test` baked into its environment and its own test database, so running the suite is a single command (`docker compose run test bin/rspec`) that can't be run against the wrong environment by mistake.

The goal is that local development and the test suite run entirely inside containers, so the app doesn't depend on the evaluator's host Ruby version, Postgres install, or native extension toolchain. The original production `Dockerfile` is left untouched, so it still demonstrates the deploy path independently of the dev setup.

`bin/docker-entrypoint.dev` runs `bundle check || bundle install` before `bin/rails db:prepare` and exec'ing the given command, so both `docker compose up web` and `docker compose run test bin/rspec` are single, self-sufficient commands on a completely fresh clone — no separate manual bundle-install or migrate step for an evaluator to remember. The check-and-install is wrapped in an `flock` against a lock file inside the bind-mounted `vendor/bundle`, since both services share that directory and could otherwise both try to install at once on a fresh clone.

That lock is a best-effort mitigation, not a guarantee: on Docker Desktop for Mac, the bind-mount filesystem (virtiofs) doesn't always propagate `flock`'s advisory lock semantics reliably across containers, so a genuinely simultaneous first run of `web` and `test` can still race and fail mid-install (confirmed by deliberately racing them). It self-heals — re-running the failed command's bundle install again succeeds, since Bundler resumes rather than restarting from scratch. In the README's documented usage (run `web`, then separately run `test`), the commands aren't issued concurrently, so this doesn't come up in practice; it only matters if someone deliberately starts both at once on a completely fresh clone.
